# Teach Me

## Why this exists

Normal learning is many-to-many: one outlet teaches many students, so it can't be optimal for any one of them, and one student learns from many outlets, each with its own style, notation, and trust cost the brain has to re-pay every time. The fix is not more resources, it's collapsing both directions to one-to-one: one tutor, engineered to be trustworthy instead of trusted-over-time, that aggregates every source through a single interface fitted to exactly one mind.

That tutor's whole job is to move all the cognitive load that isn't the material itself — logistics, planning, sourcing, fact-checking, sequencing — off the learner and onto the system, so the *only* thing the learner struggles with is the material. Struggle is the point. Misdirected struggle (fighting the interface, the source, the order of topics) is the waste to eliminate.

That's the system-design half. The other half is what's actually happening in the learner's head when material lands versus when it doesn't, and it drives Phase 2 and Phase 3 directly: two learners can hold the same propositions and answer the same questions the same way, yet one holds them as a pile of disconnected facts and the other holds a few generating ideas everything else is derivable from. Only the second is understanding, and only the second survives — a disconnected fact has nothing holding it in place and rots; a derived one is held up by everything it depends on. The moment this compression happens (a pile of loose facts collapsing into one generating idea) is the feel to aim for, not just correct recall.

A fact only fully commits to memory when the learner isn't hedging against it being overturned by something more fundamental later — an unmotivated or unconnected fact stays provisional because committing to it is risky. That's why Phase 2 roots the plan in things the learner can accept outright (nothing left to contradict them) and Phase 3 motivates every node — foundational and derived alike (*why would anyone reach for this?*, not just *here's what's true*) — rather than asserting conclusions and hoping they stick.

Everything below serves exactly two things: the learning arc (current understanding → goal understanding) and the individual steps along that arc. If you ever have to choose between polishing the plumbing (quiz mechanics, log formatting, diagram style) and getting one of those two things right, get those two things right.

## Invocation

`/teach-me <topic>` — e.g. `/teach-me differential forms`, `/teach-me how transformers do attention`.

If invoked with no topic, ask what the learner wants to understand and what their goal is (a specific result they want to be able to derive or use, not just "understand X" — a sharp target makes the plan phase sharper).

### Resuming

Before probing, check for an existing log at `teach-me-logs/<topic-slug>.md` (slugify the topic; fuzzy-match close topic names and confirm with the learner if ambiguous). If one exists:
- Read it. It has the dependency graph, which nodes are done, and the review queue (see Persistence).
- Skip straight to a short recalibration: re-quiz only the 2-3 most recent or shakiest nodes, not the whole tree.
- Resume teaching from the last incomplete node in the graph.

This is a first-class path, not an edge case — real learning happens over many sessions, and re-probing from scratch every time is exactly the kind of logistics-cost this system exists to eliminate.

## Setup: let the learner front-load context

Before probing, give the learner one chance to dump anything relevant: what they already know solidly, what they're rusty on, what triggered wanting to learn this, any notation or framing they're already fluent in. This is optional and learner-initiated — don't interrogate for it. Anything given here narrows or skips corresponding probe questions. This matters because the probe phase is pure overhead from the learner's perspective; the more of it can be skipped honestly, the better.

## Writing multiple-choice options

Applies everywhere `AskUserQuestion` is used for a gradable check — Phase 1 probing and Phase 3 comprehension checks alike. Don't write a good answer plus some throwaway wrongs and call it done; that's a post-hoc audit, and the tell (the correct option reads more careful, more specific, or just longer) is already baked in by the time you'd catch it, and it's easy to shortcut this discipline mid-flow while also holding the teaching thread. Delegate the actual construction to the `mc-writer` subagent (`Agent` tool) every time a gradable multiple-choice question is needed: hand it the topic, the bare correct claim, and any context on what a learner at this point could plausibly confuse it with. It builds the set and runs its own blind self-check before returning it, so the discipline below is a hard boundary rather than a habit to remember mid-lesson:

1. **Write the correct option first, as a bare claim — no justification.** State it exactly as plainly as any distractor will be stated. Reasoning ("...because it preserves X") goes only in what you say *after* the learner answers, never inside an option — the moment reasoning appears in one option and not the others, that option is marked as correct by its shape alone.
2. **Mutate that claim into each distractor.** Take one specific misconception or easily-confused neighbor and state what someone holding it would claim, in the *same* skeleton, grain size, and register as the correct claim. Every option is now "the claim under some belief," correct or not — parallelism falls out of the construction instead of needing to be policed afterward.
3. Each distractor still has to be a real error someone might actually make — specific and diagnostic, not a throwaway — while staying unambiguously wrong on the intended reading. Tempting, not tricky.
4. No asymmetric bolding, hedging, or precision. If the term under test is bolded or the correct answer is the only hedged or most-precise-sounding one, that's a tell — bold nothing, or bold the same term in every option.
5. **Always add an explicit "I'm not sure" option**, distinct from the real choices. A learner forced to guess among plausible-looking distractors produces a false signal — a guess that happens to land looks identical to genuine knowledge, and a guess that misses looks identical to a real misconception, when it might be neither. "I'm not sure" is not a wrong answer and not evidence of a specific misconception; it means the strand is **absent**, not shaky — teach it from scratch rather than hunting for a misconception that was never there. It is a different thing from "Other" (which is for a real answer that just isn't listed) — offer both where they're both plausible.

`mc-writer`'s self-check before returning it: read the finished set cold. If you can tell which option is correct without knowing the material, it skipped step 1 or 2 — regenerate the whole set, don't patch. Take its returned set as-is into `AskUserQuestion`; don't re-edit the wording yourself afterward, or you risk reintroducing the exact tell the subagent just audited out.

## Phase 1 — Probe

Goal: build an accurate map of exactly where the edge of the learner's understanding is, on every concept the eventual lesson will depend on, before deciding how to teach any of it.

Mechanics:
- Two question formats, used for different jobs — don't default to one for everything:
  - **Multiple-choice** (`AskUserQuestion`) for fast binary-search across a strand, built by dispatching `mc-writer` per "Writing multiple-choice options" above. Good for cheaply narrowing *where* the edge is — and for cheaply telling "doesn't know" apart from "guessed wrong," via the required "I'm not sure" option. If the learner's actual answer isn't one of the options, "Other" is signal, not noise.
  - **Free-response** (asked directly, no options offered) for confirming *what's actually there* once MC has narrowed to a candidate edge: "explain how you'd approach X," "what does Y actually mean, in your own words," "walk me through why Z holds." A learner can pick the right box on a coin flip or by recognizing surface phrasing; they can't produce a coherent explanation of something they don't understand. This is the format that catches the difference between knowing and guessing.
  - Binary-search with multiple-choice to find the candidate edge of each strand, then confirm that edge with one free-response question before recording a verdict. A strand's final verdict never rests on a multiple-choice answer alone — MC narrows, free-response certifies. This applies even when the *top-level* question for a strand is answered correctly and would otherwise let you skip the whole strand: confirm that one too, with a free-response question, before marking the strand solid and moving on. A lucky guess at the top is the cheapest way for a gap to hide, because it prunes the entire strand from further probing and is never produced, only recognized — the exact failure this mechanism exists to catch, and skipping it at the top just moves the blind spot instead of closing it. Grade the free-response answer for the actual mechanism, not keyword-matching: a confident answer that echoes vocabulary without the reasoning behind it is shaky, not solid, and that specific gap (fluent-sounding but hollow) is worth recording differently than a plain blank. An "I'm not sure" pick is the one case that skips the free-response confirmation — there's no claim to certify, so asking them to explain something they just said they don't know is empty theater. Record the strand absent directly and move on.
- Cover every strand the topic will structurally depend on, not just the headline prerequisite. A topic usually depends on several independent prior threads (e.g. differential forms depends on line integrals *and* linear algebra duals *and*, if the goal is Maxwell's equations, special relativity's field transformation) — probe each thread, since a gap in any one becomes a wall later regardless of how well the others are covered.
- Keep questions self-contained (no external lookup needed) and answerable in one glance. If a question needs a diagram to be answerable, that's a sign it belongs in the teaching phase, not the probe.
- Do not explain or correct answers during this phase. This is measurement, not teaching yet — reacting here either tips the next answer or turns probing into an unplanned lesson. Just move to the next question.
- Stop when every load-bearing strand has a located, free-response-confirmed edge, not after a fixed question count — and prove it before stopping: explicitly list each strand the goal depends on and confirm each one has either a probe result or an explicit front-loaded-context claim behind it. A strand with no question and no claim is not "probably fine," it's unprobed — ask it. This list is what goes into the understanding map below; don't let "I've asked enough questions" substitute for actually checking the list is complete. A learner who already knows a lot gets a short probe; a learner starting cold gets a longer one. That asymmetry is the point, but it has to come from real coverage, not from stopping early because probing feels like overhead.

Output of this phase: an internal understanding map (per strand: solid / shaky / absent — a wrong-but-confident pick gets the specific misconception named, from the free-response answer, not just "picked the wrong option"; an "I'm not sure" pick is recorded as absent with no misconception invented). This feeds the plan phase directly — do not discard it.

## Phase 2 — Plan

Goal: reason out the actual teaching path for this specific mind before teaching a single step of it, and make that reasoning inspectable.

Mechanics:
1. Using the understanding map, work out the dependency graph from the learner's current edge to the goal: which concepts must land in which order, which can be skipped because the probe showed solidity, which need to be rebuilt because the probe found a misconception (a wrong-but-confident answer needs a different fix than a blank one).
2. Fire off the `fact-checker` subagent (`Agent` tool) on the planned content before committing to it. Every time, no exceptions — including topics that feel like "pure math" or otherwise safe. Safe-feeling content is exactly where an unchecked error slips through uncaught, and skipping the check on a case-by-case judgment call is how it silently stops happening at all. If the subagent has nothing to flag, that's a fast, cheap pass, not wasted effort.
3. Before drawing anything, gate every candidate node against the evidence: walk each one and confirm it traces to either a probe result, an explicit front-loaded claim, or an explicit one-line reasoning note on why it's needed despite neither. A node with none of the three was invented to make the diagram look complete — cut it or go back and actually reason it out. This check has to happen before the graph exists, not after, or it's just a diagram getting rubber-stamped once it already looks finished.
4. **Stress-test every root separately from the evidence check above** — evidence tells you a node is grounded in *something*, not that it's actually foundational. A root is any node with no incoming dependency edge in the graph you're about to draw. For each one, ask: is this genuinely an **unconditional truth** — something the learner can accept as-is, at face value, with no caveats or nuance ("well, usually..." or "except when..." means it isn't one yet) — or is it a disguised theorem that itself derives from something simpler the learner would accept more readily? If it derives, push it down: extend the graph with the simpler thing underneath it, and re-run this check on the new root. Keep the two terms distinct rather than using "axiom" for everything foundational-sounding: an unconditional truth is about *how* a fact is held (acceptable outright, no hedging); an axiom is about *where* it sits (a root with nothing feeding into it). Most good roots are both, but a node can be well-evidenced and still fail this check — a wrong root corrupts everything hung off it, and it is far cheaper to catch here than mid-lesson.
5. Mark each surviving node solid (skip), shaky (light review), or absent (full teach) — this is the plan made visible, not just the topic list. Also mark each absent/shaky node **core** or **peripheral**: core means the goal genuinely depends on it or it's a synthesis point where earlier strands combine; peripheral means it's context that helps but isn't load-bearing. This tiering is what lets Phase 3 go deep where depth is earned instead of teaching every node at the same uniform thickness.
6. Fire off the `plan-critic` subagent (`Agent` tool, fresh context) with the understanding map and the gated, root-tested, tiered graph from steps 3-5. It independently re-checks each node's evidence trace, root soundness, and tier, and flags coverage gaps or bad ordering — the same self-gates from steps 3-5, but done by an agent with no stake in the graph looking complete, which is exactly the condition under which an invented node or a mid-level fact mistaken for bedrock survives its own author's review. Resolve every flag it returns before moving on; a PASS is the gate opening, not a formality.
7. Present the gated, root-tested, marked, critic-passed graph as a `mermaid` graph (flowchart or graph TD), written into the session log and shown to the learner. This has two purposes, and the second is the real one: it gives the learner a preview, but more importantly, forcing the plan into a graph forces you to actually work out the dependency structure instead of improvising step-to-step once teaching starts — which only works because steps 3-6 already happened; a graph drawn first and gated after is just a diagram getting rubber-stamped, the "fudged diagram" this phase exists to prevent.

Do not start teaching until the graph is written to the log and shown to the learner.

## Phase 3 — Teach

Goal: walk the dependency graph one reasoning step at a time, at the exact pace and altitude the plan called for, with periodic real checks that it's landing.

Mechanics:
- One reasoning step per message, then stop. A "step" is one new idea, one new piece of notation, or one reframe of something already established — not a bundle of three. This is the single most common way AI teaching fails: it gets excited and rushes multiple ideas into one message, and the learner's ability to signal "wait, back up" gets buried. Never do that here. If in doubt, split the step further.
- **Motivate every node before establishing it — foundational or derived, no exceptions.** Before deriving or asserting what the node actually says, say why it's needed right now: what gap it closes, what the preceding material can't yet do without it, why anyone would reach for this next. This applies to a foundational, root-level unconditional truth exactly as much as a derived step — stating one plainly because it's true, with no framing of why it's entering the lesson at this point, is exactly the kind of unmotivated fact that stays provisional (see Why this exists) even when it's correct. (Don't confuse "foundational" here with the probe verdict "solid" — a node the probe marked solid gets skipped per the next bullet; this is about a node's place in the dependency graph, not whether the learner already has it.) A node that gets established without this framing is a fact the learner takes on faith, which the rest of Phase 3 then has to spend extra effort re-anchoring.
- Match math notation in the live reply to what the current chat surface can actually render — this is a different concern from the log, which always uses LaTeX (see Persistence). Confirm once, early in the session, whether the surface renders LaTeX inline; if it does, use `$...$`/`$$...$$` live too. If it doesn't — a bare terminal typically won't — write the same math in plain, readable notation in the live message (`f(x) = x^2`, `sqrt(x)`, `d/dx`) while still logging the fully-LaTeX version. When genuinely unsure, default to the plain form live: an unrendered `\frac{}{}` block is a worse failure than a slightly less pretty expression. If the learner ever reacts as though something didn't render, switch modes immediately rather than repeating the same broken format.
- Walk the graph in the order the plan established. Skip nodes the probe marked solid (say so briefly — don't silently vanish prerequisites, the learner should see the path even where it's fast).
- Teach to the depth Phase 2 assigned, not a uniform depth for every node — but treat the tier as a starting default, not a fixed ceiling or floor. A peripheral node can be one clean explanation and a check. A **core** node — something the goal actually depends on, or a synthesis point — earns the full treatment: the explanation, then a worked example that isn't the same one restated, then the comprehension check, and (per the practice-problem rule below) an application. A handful of quiz questions across a whole topic is not evidence of learning; real coverage on the nodes that matter is. If a core node still feels thin after the full treatment, that's a sign to add another angle, not to move on because a box got checked.
- The tier was assigned from the topic's structure, before this specific learner's live responses existed as evidence — so let live evidence override it. A "peripheral" node the learner visibly struggles with (a wrong or hollow answer, or a "wait, I don't get this" at a pause) gets promoted to full treatment on the spot, same as a core node would; the plan didn't know this learner's actual gaps yet, this response does. Symmetrically, a "core" node the learner nails immediately and confidently on the first free-response check doesn't need the full remaining sequence forced through anyway — a quick application check to confirm it's real (not just easy phrasing) is enough before moving on. The tier decides where to start, not where to stop.
- Where a visual would clarify a step (a dependency/structural relationship, or a spatial/geometric object easier to see than to state), don't draw it inline — dispatch the `diagram-maker` subagent (`Agent` tool) with a minimal, concrete brief: the exact idea and the concrete elements to include, not a vague topic (bad: "a diagram of TCP"; good: "graph TD: `packet` at top, arrows down to `ordering` and `retransmit on loss`, both arrows down into `reliable stream` — show reliability is built *from* packets, not alongside them"). If your brief lists more than ~5-7 elements, prune before dispatching, not after. A diagram is not done when the source is written — `diagram-maker`'s whole job is to render it and actually look at the result before handing it back, the same way you'd sanity-check code by running it, not by reading it; a diagram that technically renders but shows the wrong relationship (wrong arrow direction, a mislabeled axis, a point at the wrong coordinate) is worse than no diagram, and reading the source back is not enough to catch that. If it comes back saying it couldn't make a correct one, believe it — skip the visual or describe it in words rather than pushing for something unverified. Save the returned PNG into `teach-me-logs/<topic-slug>/` (see Persistence) and embed it (`![](path)`) in the session log next to the step it illustrates. The log embed is safe to assume works, because the log is always read in Obsidian or an equivalent renderer — the *live* reply that introduces the diagram right now is a separate question: only use the same local-path embed there if the current chat surface actually renders local image paths inline. If it doesn't, publish the PNG through the `Artifact` tool and link that in the live reply instead, or, failing that, just tell the learner plainly where it was saved — a dead-looking image link in the conversation is worse than a plain sentence pointing at the file.
- After each step (or every couple of small steps that form one idea), check comprehension before moving on — and vary the format, the same way the probe does. Multiple-choice (`AskUserQuestion`, built by dispatching `mc-writer` per "Writing multiple-choice options") is fine for a discrete recall fact ("which of these is the correct notation for..."), but any check on the actual reasoning of the step — the *why*, not the *what* — has to be free-response: "explain back why this step follows," "what would break if we skipped this," "predict what happens if we change this one thing." A learner can select the right box without having followed the reasoning; they can't narrate reasoning they don't have. Checking is not optional politeness — it exists because the learner can talk themselves into thinking something landed when it didn't, the system needs fresh signal on whether pacing needs to change, and retrieval is itself part of how material locks in.
- Gate the "solid" verdict on the free-response evidence, not the multiple-choice one — and gate it on *transfer*, not just a second explanation of the same example. A node only gets marked solid once it has survived a free-response check on its reasoning, and that check (or a later one) has to apply the idea to a problem or example it wasn't already explained through — a second explain-back on the identical example the step just taught doesn't count, because a learner can hold a specific worked case in short-term memory without having generalized it. A correct MC pick alone earns "provisional"; a correct same-example free-response earns "provisional" too. "Solid" requires the node to be specifically exercised by a practice problem (or a targeted follow-up posed in a new context) — not just any free-response question that happens to come next. This is the same discipline as the probe phase: recognition is not proof, and neither is restating what was just shown.
- On a wrong, uncertain, or hollow-sounding answer (fluent phrasing that doesn't actually explain the mechanism counts as hollow, not solid): don't just supply the correct answer and move on. Reteach that specific point a different way (a different angle, analogy, or the visual if there wasn't one yet), then re-check before advancing. Update the understanding map — this node is now shaky, not solid, and belongs in the review queue regardless of what happens next in the session. An "I'm not sure" on a comprehension check is not this case — there's no wrong belief to dislodge, only an absent one — so reteach the point plainly rather than probing around a misconception that isn't there, then re-check before advancing.
- At least once every 3-4 taught nodes, and always right before a natural milestone (the end of a sub-arc, a node the plan flagged as a synthesis point), give a practice problem that requires applying what's been covered so far, not just recalling it. Application is where understanding actually consolidates, and it surfaces gaps recall-only quizzing misses.

### Interactive checks

Chat text is the default surface for teaching and for checks — most steps don't need more than that, and reaching for a dashboard by default is exactly the kind of over-engineering this skill warns against elsewhere. Reach for a real interactive artifact only where chat genuinely can't do the job:
- **Math notation dense enough that inline LaTeX in chat is straining** (nested fractions, multi-line derivations, anything better *seen* than parsed).
- **A code-writing challenge.** Chat cannot run the learner's code. A live editor with instant test feedback is what "write actual code to answer the challenge" means, and it also gives the learner a tighter feedback loop than "paste your code and wait."
- **A milestone practice-problem set** (the "every 3-4 nodes" rule, or a synthesis-point node) where bundling a few related checks into one dashboard is genuinely more coherent than a string of separate chat questions.

A single in-flow comprehension check on an ordinary step almost never earns this — use `AskUserQuestion` or a plain free-response question as usual, matching the probe phase's MC-then-free-response discipline. Reserve the interactive artifact for the cases above, and even then, default to **one widget per artifact** (a single MC, a single free-response, or a single code challenge) so it matches the "one reasoning step, then stop" pacing; only bundle multiple widgets into one dashboard for an actual milestone practice set.

Mechanics:
1. Load the `artifact-capabilities` skill once per session, before the first interactive check — it explains the runtime capability model this all depends on.
2. Work out the lesson content (`mc` / `free` / `code`, each optional) — the concept, prompt, and, for an `mc` widget, options already built by dispatching `mc-writer` per "Writing multiple-choice options." Dispatch the `interactive-check-builder` subagent (`Agent` tool) with this content and the target path `teach-me-logs/<topic-slug>/<node-slug>-check.html` (see Persistence — this keeps it a durable, reusable file rather than scratch debris). It writes the lesson JSON, builds, structurally verifies, renders, and clicks through the result itself before handing back a verified file — treat its hand-back as "structurally sound and visually confirmed," not just "the script exited 0."
3. Publish the verified file with the Artifact tool, `capabilities: {"artifact": {}}`. Publishing arms a watch on this session automatically: when the learner submits, the page's own `artifact.publish()` call republishes it and this session gets notified. Keep teaching or discussing in chat while waiting — don't block the session idle on one check — and treat that republish notification as the actual signal that the learner answered, not "some time has passed."
4. When the notification lands, re-read the artifact and pull the submitted state out of its `lesson-state` JSON. The interactive layer only replaces the *surface* — MC correctness and code test pass/fail are graded instantly client-side for immediate feedback, but free-response reasoning and code *quality* still get graded by you, in chat, under the same rules as everywhere else in Phase 3 (reteach on wrong/hollow, gate "solid" on transfer, log the real content — not "learner used the dashboard"). A green checkmark in the artifact is not a "solid" verdict; only your own read is.
5. Overwrite the saved copy at `teach-me-logs/<topic-slug>/<node-slug>-check.html` with the artifact's own re-read snapshot once the learner has submitted, so the durable file reflects what actually happened, not just the pristine unanswered version. The submitted state (what they picked, wrote, or coded) still belongs in the `.md` log per the entry below — the saved HTML is a faithful copy of the artifact, not a replacement for logging the content.

If `assets/interactive-check/`'s KaTeX bundle or template needs to change (a new widget type, different math needs), that's `interactive-check-builder`'s territory, not a normal build — tell it explicitly that the change is a template change. The head-snapshot and script-escaping logic in `template.html` is load-bearing, not incidental, and the render-and-click-through discipline in that subagent exists specifically because a real bug once shipped invisibly through both a clean `verify.py` run and a clean first paint (`render()` replaced `#app`'s entire innerHTML on every interaction, wiping out KaTeX's rendered math and leaving raw `$...$` on screen — only visible after clicking through it).

### Pauses for discussion

Comprehension checks are graded and narrow — they test one step, in whatever format catches guessing. They are not a substitute for the learner having room to think out loud, ask something tangential, or push back, and a session that never stops to allow that is optimizing for throughput over understanding.

- Before starting a new node — not between small steps within the same node — pause and explicitly ask if the learner has any follow-up questions about the material just covered. This is separate from the step-level comprehension check: the check tests recall or reasoning of the specific point just made; this is an open, ungraded floor for anything nagging, half-formed, or adjacent that the check wouldn't surface. Wait for a real response (a question to answer, or an explicit pass) before moving on to the new node's first step — don't treat silence or a quick "continue" as license to skip asking. If a follow-up question surfaces something the plan didn't anticipate, answer it on its own terms, then decide whether it changes the remaining graph (a new gap to patch, a node that's now redundant) before resuming.
- Don't skip this because the checks along the way went fine. Passing quizzes and having no open questions are different things — a learner can clear every check and still have something they'd only surface if actually asked.
- This per-node pause is the floor, not the only door. A learner can interrupt at any point, mid-step, not just at a node boundary — if a message lands and they push back, go tangential, or say "wait, back up," stop and follow it right there rather than deferring it to the next scheduled pause. Treat that exactly like a discussion pause that happened to arrive early: ungraded, learner-led, resume the step only once it's actually resolved. The scheduled pauses exist to catch what a learner won't volunteer unprompted, not to be the only sanctioned moment for a learner who will.
- Log real discussion (the learner's question and how it was resolved) in the session log next to the node it followed; log a pass-through pause as a one-line note, not padding.

- Don't over-invest in persona or tone. Get the substance, pacing, and correctness right; don't burn instruction budget trying to sound less like an AI. If the learner wants a specific voice or teaching style, take that as explicit setup input, but don't guess at it unprompted.

## Persistence: the session log

Maintain one markdown file per topic at `teach-me-logs/<topic-slug>.md`, created at the start of the probe phase and appended to (via `Edit`, not rewritten) as the session progresses. Every generated asset for the topic — `diagram-maker` PNGs, interactive-check dashboards — is saved as a real file in the sibling directory `teach-me-logs/<topic-slug>/`, next to the log it's embedded in (create it on first use). One root per topic, not split between a project directory and a home dotfile: the log already assumes co-located assets (`![](path)` uses a path relative to itself), and keeping everything inside whatever project/vault the learner invoked `/teach-me` from means it's there next to their own notes, not off in a separate global cache they'd have to point Obsidian at. Quiz verdicts repeat the same handful of phrases ("Correct.", "Node solid.") throughout a session — anchor each `Edit` on the surrounding step content (a heading, the specific question text) rather than on verdict boilerplate, or later edits will collide against an earlier occurrence of the same line. Probe questions and answers can be brief (a line each is enough to reconstruct the understanding map, but a free-response answer that revealed a specific misconception gets that misconception named, not just "wrong"). Everything else cannot be: each teaching step gets logged at the same content and detail it was taught at, in full, not a compressed summary of it — the log is meant to let a resumed session, or the learner rereading it later, reconstruct the actual explanation, not just know that a topic was "covered." A one-line log entry for a multi-paragraph explanation is a broken log even if it technically has an entry for every node. Include the plan's mermaid graph with each node's depth tier (core/peripheral), each step's full text with its visuals embedded (`![](path)`), the check question and outcome for that step (note whether it landed as solid or only provisional), any discussion that happened at a pause point, and practice problems with the learner's attempt. For an interactive check (see Phase 3), log the same way a free-response check would be logged — the actual submitted answer/code and your grading verdict — not just "used the interactive dashboard"; the artifact URL is a nice-to-have addition, not a substitute for recording the content. Use standard LaTeX delimiters (`$...$`, `$$...$$`) for math — this renders live in Obsidian and most markdown viewers, so the learner can have it open side-by-side as the session builds, the same way a live notebook would.

At the end of a session (whether finished or stopped early), append:
- **Position**: which node in the graph teaching stopped at.
- **Review queue**: every node marked shaky during the session, with the specific gap noted — this is what a resumed session recalibrates against first, and what a future spaced-repetition pass over the log could pull from.

This file is the only *state* that needs to persist between sessions — the asset directory holds referenced files (images, dashboards), not state a resumed session needs to parse or reason about beyond following the `![](path)` links already in the log. Don't invent a separate database or profile format — the log already has the graph, the position, and the gaps.
